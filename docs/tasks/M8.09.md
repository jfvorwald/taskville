  - Longest event-loop block: measured as the largest gap between 1 ms `setInterval` ticks around each request. For state seeks it equals the whole request: the chunked replay never yields, so a near-end seek blocks the engine (live ingest, SSE, the permission bridge) for 8 to 35 s. `monitorEventLoopDelay` reported only 1 to 4 ms max and was discarded as not capturing the block.
  - Where the time goes (head replay split, 3 runs, no HTTP): SQLite read plus `JSON.parse` 839 to 1,091 ms, `domainReducer.apply` 7,895 to 10,511 ms. The reducer is about 90%, roughly 40 to 50 us per event at this state size (M6.01 measured about 22 us per event on a 50,000-event live day), so per-event cost grows with the state (56 agents, about 4,600 tasks at the head). Faster reads alone would not help; only skipping replayed events does.
  - Timelines listing and event paging are within budget; only state seeks miss.
  - Suggested fix for the follow-up tickets (Owns `apps/engine/src/timelines/**` and archive checkpoint storage in `apps/engine/src/storage/**`):
    - Storage: a new `archive_checkpoints` table in `src/storage/migrations.ts` (next migration after V4), keyed `(archive_id, position)` with `reducer_version`, `state_hash`, `state_json`, mirroring `checkpoints` but referencing `archives(id)`, never the live `(project_id, sequence)` table; accessors on `SqliteArchives` (or a sibling in `src/storage/archives.ts`), deleted with the archive in `SqliteArchives.delete` so retention pruning removes them. Validate with the existing `trusted()` check (reducer version, head, project, hash), so they stay disposable caches.
    - Interval: 1,000 positions, equal to `archiveReplayChunk`, so a seek loads one checkpoint and reads at most one chunk (at most 999 events, about 50 to 80 ms of reducing at the measured per-event cost). 200 rows per full archive; head state JSON is about 155 KB, so roughly 15 MB per 200,000-event archive (up to 5 kept per root). ARCHITECTURE.md's 500 would halve the tail but double the storage to about 30 MB per archive; 2,000 would leave about 160 ms of reducing at the tail on a loaded machine.
    - When to build: the first seek cannot meet 300 ms without checkpoints already stored, so build them once after the archive is written (or lazily on the first seek), in a pass that yields to the event loop between chunks, as `ImportJobs.#read` already does with `yieldToEventLoop()`. The state route should also yield between chunks for any replay that falls back to the uncheckpointed path.
    - Test: checkpointed state and `stateHash` equal a full replay of archive events 1..at (checkpoint equivalence, ARCHITECTURE.md 14), plus a stale-reducer-version or corrupted checkpoint falling back to replay.
- **After (implementation):** `archive_checkpoints` (migration V5, STRICT, keyed `(archive_id, position)`, references `archives(id)`), a row every 1,000 positions, built lazily after the first state seek by `ArchiveStates` in `apps/engine/src/timelines/archive-state.ts`. A seek loads the nearest trusted checkpoint (`trusted()` from `storage/checkpoints.ts`) and reduces at most 999 events; untrusted rows are deleted and skipped. One build per archive at a time (concurrent seeks share the in-flight promise); it yields between 1,000-event chunks, writes one row per small transaction, and stops quietly when the archive is gone (the insert is conditional on the archive row existing). Replays without checkpoints yield between chunks too. `archives().delete` removes the checkpoints. Same 200,000-event lively archive (4 simulated days, seeds 42 to 45, written with `archives().complete`), in-process engine, script `/tmp/m809/measure.ts`, machine load average 15 to 20 from other agents:
  - First seek (no checkpoints, at 199,000): 6,700 ms, longest event-loop block 222 ms (was the whole request). Build finished about 8.5 s later, 200 rows.
  - Median of 5 with checkpoints: at 199,000 15.6 ms; at 199,500 27.1 ms; at 200,000 (head) 14.6 ms; at 100,500 24.7 ms (300 ms target met by about 10x). Longest event-loop block 17 to 199 ms (one outlier per position, GC or load).
