### Diagnostic run (not committed): heap after a forced GC

An in-process engine (`bootEngine`, no HTTP) fed the same 8 hours of seed-42 demo events as fast as possible, with `node --expose-gc` and two `gc()` calls before each sample:

```text
calm:   hour 1 heapUsed 16.6 MiB, rss 144.5 MiB ... hour 8 heapUsed 16.7 MiB, rss 181.8 MiB
lively: hour 1 heapUsed 17.1 MiB, rss 198.1 MiB ... hour 8 heapUsed 12.3 MiB, rss 163.0 MiB
(calm rss by hour: 144.5, 145.8, 139.8, 171.6, 169.2, 157.7, 167.7, 181.8; external 6.0 MiB throughout)
```

Retained JavaScript heap is flat, so this is not a leak of objects; RSS moves about 20% between samples on allocator and page retention plus native memory (SQLite), driven by per-batch churn: each batch parses and re-serializes a projection JSON that itself grows linearly (#167). #166 lists the next steps; #168 asks the owner whether SC-006 should measure memory after GC.

## How the checks work (`tests/perf`)

- `engine.ts` spawns the real `node apps/cli/src/main.ts serve --headless` in a throwaway home on a free port, reads the CLI token, and talks HTTP; RSS is `ps -o rss= -p <pid>`, the median of 5 samples 100 ms apart.
- `viewer.ts` is a connected viewer: one `fetch`-streamed SSE subscription (the CLI's `readSse`), recording arrival times of probe events and checking that ingest sequences arrive contiguous.
- `batch.ts` (SC-004): runs the M1.12 bench (`apps/engine/src/ingest/bench.ts`) as is, then posts five 1,000-event batches of demo events to the spawned engine and times each request to its 200.
- `latency.ts` (SC-005): 1,000 single-event probes, 10 ms apart, timed from just before the POST to the moment the viewer parses the frame; once on an idle engine, then again while the six-agent demo (lively, 60x) streams into the same project. Pass on p95 under 250 ms and no gaps or duplicates.
- `soak.ts` (SC-006): posts the demo's 8 hours (seed 42) through `runProducer` at a 480x virtual clock with the viewer attached; at each simulated hour, after the viewer has every earlier event, samples RSS and sizes the snapshot state (agents, sessions, tool calls, tasks, requests and open ones, commands). Calm is the spec scenario and decides the verdict; lively is an extra, heavier run reported alongside.
- `run.ts` prints the report and exits 1 on any miss. `pnpm perf [all|batch|latency|soak]`; `pnpm perf:unit` runs the helper tests with `node --test`. None of it is in `pnpm check`.

## Paths outside Owns

- Root `package.json`: `perf` and `perf:unit` scripts.
- Root `tsconfig.json`: `include` gains `tests/perf`, so the perf scripts are typechecked by `pnpm check`.

## Lessons

- RSS at this scale (about 120 to 200 MiB, a few MiB of real state) is dominated by allocator and page retention, so two runs of the same seeded input differed by 12 points of "growth". A memory criterion needs either a retained-memory measure (heap after GC) or a long steady-state run, or it measures noise.
- The demo exposes unbounded state that unit tests never would: closed requests, terminal tasks, and finished subagents accumulate linearly (148 KiB after 8 calm hours, 474 KiB lively).
- Workspace packages do not resolve from a root-level `tests/` directory (no root dependency on them), so the perf scripts import sources by relative path; the engine's own dependencies (for example `pino`) also do not resolve there, which is why the engine runs as the real spawned CLI.
