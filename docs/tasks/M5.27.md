- **Lessons:** A PID lock breaker must re-check the holder after finding it dead: a holder that released and exited may already have been replaced by a live one. Under Node 26 the `JSON.parse` message names the kind of corruption ("Unexpected end of JSON input" is an empty or cut line; interleaved writes give "Expected ',' or '}'"). ## Root cause (debugger round)

The CI failure on PRs #351 and #357 (`SyntaxError: Unexpected end of JSON input` at the spool line check) was real corruption, not a test race: the test waits for every shim to exit before reading, no writer outlives its shim, and nothing renames the main file.

In `break_stale_lock` in `apps/cli/hooks/claude-code-shim.sh`, a waiter read the holder's PID, ran `kill -0`, then moved whatever lock was at the path. If holder A released and exited in between and live shim C took a new lock, the waiter moved C's live lock away. Two shims then appended at once, and one shim's torn-line repair (`tail -c 1` then `printf '\n'`) could add a stray LF, which produces the empty line behind "Unexpected end of JSON input".

## Fix

After `kill -0` finds the PID dead, the breaker reads the lock's PID again and breaks only if it is unchanged. A dead holder can no longer release, so a lock that still names it is the stale one. The header comment that claimed this was already safe is corrected.

## Tests

- New: "never breaks a live lock that replaced the one it judged stale" runs a copy of the real shim that pauses right after the first PID read, so the interleaving is deterministic. Failed under `/bin/sh` and `/bin/dash` before the fix.
- Mutation checks: with the re-read removed, the new test fails under both shells; with `acquire_lock` stubbed to `return 0`, the existing concurrency test fails under both shells.
