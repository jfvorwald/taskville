## The rule

`redactJson` is the one shared rule for ingest and evidence. It now seals the whole value of a sensitive property name (`password`, `apiKey`, `token`, ...):
- Any string, number, boolean, object or array there becomes one `[REDACTED:sensitive-value]`, keys inside it included. So `{ password: { value } }`, `{ token: 123 }` and `{ password: { hunter2: true } }` keep nothing.
- `null` stays, since it carries nothing. A placeholder string directly under the key (`$DB_PASSWORD`, `***`, empty) stays readable, as before.
- A sensitive key nested inside ordinary objects is found at any depth.
- `skip` is respected, and `__proto__` stays data.
- The sealed value gets one mask entry at its path.

The first version kept the structure and masked each scalar inside it. roborev 5260 showed that keys inside a sensitive value would then survive, so the whole value is sealed instead.

The evidence-only copy from M2.06 (`maskSensitiveSubtrees` in `apps/engine/src/evidence/body.ts`) is removed, and evidence now calls the shared rule. M2.06 already sealed every non-string, non-null value of a sensitive key, so stored evidence bodies are byte-identical to what M2.06 wrote.

## Old events and the dedupe hash

- **Event log:** no stored event can be affected. Every payload a producer may send is a strict schema with no sensitive-named field and no free-form object. The one free-form object, `command.requested.payload`, is engine-only, and the pipeline rejects it from every source until M4. So the masked payload of every event ingested before the fix is unchanged. A retry hashes the same and is a `duplicate`, never a `conflict`. The fix matters for M4, when the engine writes `command.requested`, and as the single rule behind evidence.
- **Evidence:** bodies are byte-identical to M2.06's, so hashes and content-addressed dedupe are unchanged. A body is also stored once per tool call and part (first write wins), so a retried hook never conflicts.
- **Spool:** events spooled before the fix are mapped and masked when they are replayed, under the current rule.

## Lessons

- A redaction rule written as "the value of a sensitive key" has to say what happens to non-strings, to what is below the key, and to the keys below it. Sealing the whole value is simpler and leaks nothing; keeping the structure leaked keys.
- When a diff masks per line, mask the line before adding the `+`/`-` prefix, or the prefix becomes part of the token being checked.
- Before documenting a hash migration, check which payloads can actually carry the shape. Here the strict schemas meant no stored event could change.
