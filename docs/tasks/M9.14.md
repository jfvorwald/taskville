- **Root cause:** `useBreakPlan` read `store.now()` during render. Bubbles calls a no-op `setBubbles` several times a second; under load React renders for one, bails out, keeps that render's hook state and drops its effects. A bailed-out render returned the new plan, so Bubbles' `[plan]` effect deps moved forward without the effect running, and the next real tick saw no change. The chatter bubble never appeared (the wave's poll got `[]` for the full 60 s). In the live app it heals at the next plan change, but a bubble can be stale or missing and the city can miss a break starting until then.
- **Fix:** `usePlan.ts` reads the clock only when a tracked input changes (the 1 s tick, store data, Break time, strict attribution, lighting), so a bailed-out render gets the same plan; the plan stays at most 1 s behind, as before. Regression test: two updates that cancel out force the bail-out render on an idle machine; it failed on the old code with the wave's exact symptom and passes now.
- **Lessons:** read the failing assertion before raising timeouts again (this was not a timing flake); a hook must not read an untracked value such as the clock during render; two cancelling state updates turn this class of load flake into a deterministic test; reproduce with the neighbouring test folder, not only CPU burners. Investigation by the debugger.
