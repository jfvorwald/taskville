## What changed

- **Keypress link (#174 default).** On a terminal (`stdin.isTTY` and `setRawMode`), `serve` puts stdin in raw mode and prints `Press p for a new pairing link (valid for 10 minutes); Ctrl-C stops the engine.` Pressing `p` or `P` prints a fresh one-time link, valid for 10 minutes, on the serve terminal's stdout only (never in the log).
  - **Rate limit:** at most one code per second (engine clock; a clock that went back does not lock the key out). At most one request per input chunk, so a pasted run of keys counts once.
  - **Outstanding codes:** at most five unexpired, unused codes; past that the oldest stops working. Earlier codes keep working until used or expired.
  - **Ctrl-C:** in raw mode Ctrl-C arrives as a byte and stops the engine like SIGINT.
  - **Terminal restore:** on the normal stop, SIGINT or SIGTERM, any failure after the keys are attached, and process exit. If the terminal refuses raw mode, partial setup is undone and `serve` falls back to the no-terminal behavior.
- **No terminal:** `serve` prints the one startup link and `For a new pairing link later, restart taskville serve.`, as before, and never touches stdin.
- **Persisted pairings (#113 default):** `SqlitePairingRecords` (the `pairings` table, SHA-256 digests only) is wired through a small deferred adapter, because `createApp` needs the `PairingStore` before `bootEngine` opens storage. Nothing can pair before the server listens. Codes are never persisted. `taskville unpair` clears the table through the existing revoke route.
- **Startup failures:** any failure after the server listens now closes it as well as the databases.
- **`composeServe` (exported)** builds everything `serve` runs without listening, so the route table is testable. `run` keeps the M2.07 spool replay (before listening) and drain (after), unchanged in behavior.

## Forced changes outside Owns

- `apps/engine/src/auth/pairing.ts` and `apps/engine/test/auth/pairing.test.ts`: `PairingStore` held one pending code and replaced it on every issue, which contradicts "the previous unexpired code still works". New option `maxPendingCodes` (1 to 16). The default of 1 keeps the old behavior, and every existing test passes unchanged. With more than 1, each code has its own 10-minute clock, exchange compares against every outstanding code, and the oldest is dropped past the cap. `unpairAll` clears them all.
- `apps/cli/src/context.ts`, `apps/cli/src/main.ts`: an optional `stdin` on `Io` (a minimal `KeyInput` shape), passed as `process.stdin` by `main`. Merged alongside M2.08's `confirm`.

## Security: an agent that can read the home, run `taskville`, and send signals

- **Minting a code needs the serve terminal.** Codes are created only in the `serve` process: at start, and on a `p` read from its own controlling terminal's input. They live in memory and are printed only to that terminal's stdout.
  - No HTTP route mints one: the route-table test pins the whole table, and the only pairing routes are the exchange and the revoke.
  - There is no IPC, and no signal handler mints one: `serve` handles SIGINT and SIGTERM only, both of which stop it.
  - Every `taskville` command reaches the engine over HTTP with the CLI token, so none of them can mint a code.
- **Reading the home yields nothing usable for pairing.**
  - `token` and `bridge-token` authorize no pairing.
  - `taskville.db` holds SHA-256 digests of 256-bit session secrets (the restart test greps the file and the WAL for the raw secret), not invertible.
  - Codes are never written anywhere.
  - `evidence.db` and the spool are unrelated.
- **Signals** can stop `serve` (denial of service, visible to the human) but not mint.
- **Residual paths**, outside what the design can stop (ARCHITECTURE.md 13 threat model limit), stated so they can be weighed:
  1. **An engine run the agent starts.** The agent stops the human's `serve` and runs its own. Its startup link goes to the agent's stdout, and with persistence the paired session survives into the human's next run. That is no cheaper than writing a digest into the `pairings` table, which #113 accepted. Decision ticket #198 asks whether to require a confirmation at the serve terminal before a session from another run may send commands (M4).
  2. **A terminal the agent can drive.** Inside a shared tmux or screen server (`send-keys` plus `capture-pane`), or through AppleScript into Terminal.app, a same-user process can both press `p` and read the output. Injecting keys with `TIOCSTI` (which Linux 6.2 and later can switch off) would let a process press `p`, but not read the printed code. tmux, screen and AppleScript are the routes that do both.
  3. **Redirected output.** `taskville serve > file` with stdin still a terminal puts every printed link in that file. The keypress itself still needs the terminal.

## Lessons

- A single-slot design ("issuing a code replaces the previous one") turned a small feature ("old codes keep working") into a change to a security module. The option keeps the default behavior, so no existing test had to move.
- In raw mode the terminal stops turning Ctrl-C into SIGINT. Raw mode means owning shutdown, and every exit path has to restore the terminal: two of the three review findings were exit paths that did not.
- Rebasing onto a ticket that edited the same function (M2.07's spool in `serve`) is new code, so the panel ran again on the result and found a real issue.
