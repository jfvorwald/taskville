- **Lessons:** The window Escape listeners (history, panel, city) re-register on their own deps, so their order shifts with selection and mode changes. A test that pins the bug must fix the worst order (history registered last, by selecting before entering history) or it passes intermittently.

## Red

Test file: `apps/web/src/history/ui/history-escape.browser.test.tsx` (real HistoryProvider, HistoryControls, AgentPanel and city InteractionLayer in a Canvas, listening on the window as in the app).

Command (from `apps/web`):

    pnpm exec vitest run --config vitest.browser.config.ts src/history/ui/history-escape.browser.test.tsx

Result: 2 failed, 1 passed, stable over 3 runs.

- FAIL "returns to live and keeps the agent selected with the panel open": mode returns to live, then `expected null to be 'a1'` (the panel and city listeners cleared the selection).
- FAIL "does the same when focus is inside the panel": same assertion, focus on the Files tab.
- PASS (guard, passes today) "in live mode Escape still clears the selection and closes the panel".

Probe: pressing `l` instead of Escape in the history cases keeps the selection, so the Escape listeners are the cause. A first attempt used a nonexistent `page.keyboard` API (TypeError); fixed to `userEvent.keyboard`.

## Green

Change: `apps/web/src/history/ui/HistoryControls.tsx`. The history keydown listener is registered in the capture phase and, for Escape only, calls `stopPropagation()` before `history.exit()`. The panel and city listeners (bubble phase) never see that Escape, so the selection and open panel survive the return to live. `l` and live-mode Escape are unchanged.
