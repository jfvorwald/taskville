## The scenario

Ada dispatches (Dispatch), Brook and Cyd implement (Workshop), Dee tests (Test Lab), Eli reviews (Review) and sends security-reviewer subagents (Security), Fay documents and researches (Archives). Tasks flow created -> assigned -> running -> handed to Dee -> sometimes back for a fix -> handed to Eli -> reviewing -> completed -> commit and merge -> documented by Fay; at most four are open at once so work flows instead of piling up. Brook sends explorer subagents; every 12 to 18 simulated minutes Ada leads a small in-process team whose teammate shares her session and messages her with `SendMessage` (a tool call, as the adapter will surface it). Shapes follow `fixtures/events/crew.jsonl` (S-2): a subagent registers without a parent, and a second `agent.registered` adds the parent when the Agent tool call returns. Trouble comes from turn failures and occasional failed tool calls; idle agents end their turn (waiting) and resume with a new prompt.

Pace: each step is one visible change, `changeMinMs` to `changeMaxMs` after the previous one on the virtual clock (calm 5 to 15 s, lively 1 to 3 s, or custom). Needs-you moments come every `needsYouMs` +-20% (calm 3 min, lively 90 s), the first within 40 to 90 % of that.

**Needs-you choice.** The demo source is `demo:<seed>` with `demo` provenance; `producerPolicyViolation` accepts `request.opened` from it, and only `taskville:bridge` can make a request answerable (M1.08). So each needs-you moment is a telemetry-only permission request: the agent opens a Bash call and a `permission` request, the city shows red with "Open session" only, and the request closes as `answered_elsewhere` when the agent's own tool result arrives 3 to 8 maximum change intervals later, as if answered in its terminal. While it is open, nothing else happens on that session (subagents and teammates share it), so the closing event is exactly that tool result. The demo never emits engine-only types (`request.resolved`, `command.*`, `project.created`).

**Determinism.** One mulberry32 stream drives every choice; time is simulated milliseconds from `startAtMs` (default 2026-01-01T09:00Z offline). Same seed, pace, and start time give the same steps and stateHash; a shorter run is a prefix of a longer one. Event keys are `r<startAtMs base 36>-e<n>`, so re-running the same run is all duplicates and any other start time is a new run. The six core agents keep the same IDs across runs (the same bots in the city); subagents, teammates, tasks, tool calls, requests, and teams are per run.

**Purity.** `packages/demo/test/purity.test.ts` is the domain package's scan (no Node built-ins; no clock, randomness, timers, or host globals; `Date.UTC` and `Date.parse` allowed). Timestamps are formatted by arithmetic (`isoFromMs`, tested against `toISOString`). The producer gets `post`, `sleep`, and `now` injected and schedules each step at `start + atMs / speed` on that clock.

**Offline storage.** `toStoredEvents` validates each event and the producer policy, stores `reason` as `{ text, masked: false, truncated: false }`, sets `receivedAt` to `occurredAt`, and uses deterministic event IDs. Masking is a no-op by construction: a test runs every string the scenario writes through `redactText` from `@taskville/adapters/redact` and requires it unchanged, and reasons stay under 280 characters.

## Notes for the CLI (#18) and ingest (#13)

- `demo start` should pass `startAtMs: Date.now()`, `now: Date.now`, a `setTimeout`-based `sleep`, and `stop` tied to SIGINT; map `DemoIngestError` with `unknown_project` to exit 2.
- `demo run --offline` prints `runOffline(...).stateHash`; offline hashes are not comparable to an engine run's, because the engine assigns its own event IDs and receive times.
- With engine ingest, demo `reason` text goes through real redaction; the no-mask test keeps the two paths equal.

## Lessons

- An agent-as-generator design (each agent yields one visible change at a time; the orchestrator picks who moves) made the scenario easy to read and deterministic, and blocking a whole session during a needs-you moment fell out naturally.
- Same-session closure (`answered_elsewhere` on the next event from the session) means subagents and in-process teammates can close their parent's request, because they share its session (S-2). A producer that wants a request to stay open must hold the whole session, not just the agent.
- Identity for repeated runs needs deciding up front: stable core bots, per-run transient agents and tasks, and a millisecond run tag in event keys. The review found each of these separately.
