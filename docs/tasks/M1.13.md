## Routes

- `GET /v1/projects`: every project with `id`, `name`, `roots`, `builtin`, `head`, sorted by ID (Unsorted always present after boot).
- `GET /v1/projects/:id/snapshot`: projection and head read in one transaction, so `cursor` is the head the state was computed at. A missing or stale projection is answered by replaying the log, without writing. `attention` is `attention(state, now)` with the engine clock at read time, so the heuristic `silent` record appears and goes with the clock while `stateHash` stays the stored one. `404 unknown_project`.
- `GET /v1/projects/:id/events`: `Last-Event-ID` wins over `?after`, default 0; a cursor that is not a non-negative integer is `400 bad_request`; unknown project `404`; `after > head` sends `resnapshot` `cursor_ahead_of_head` and closes.

## How the stream avoids gaps and duplicates

- Backlog comes from storage in pages of 256, so a long backlog never sits in memory. When a page reaches the head, the subscriber goes live in the same tick: storage reads and hub offers are synchronous on one thread, and ingest publishes only after COMMIT, so no commit can fall between the read and the switch.
- `lastQueued` is the highest sequence read or queued. A live event at or below it is dropped (repeated or late broadcast). One above `lastQueued + 1` means a broadcast was missed (a crash between COMMIT and publish, or another connection committed), so the subscriber reads storage again from `lastQueued`. Idle heartbeats compare the head too.
- Live frames wait in a queue of at most 1,000. A client that stops reading fills it and gets `resnapshot` `slow_consumer`, queued behind the frame already in flight, then the stream closes and the subscriber leaves the hub at once. Other subscribers are unaffected.
- Client disconnect (`onAbort`) and engine shutdown (`hub.close()`) both remove the subscriber; shutdown aborts the stream so the socket ends without waiting for a stalled reader.

## Done-when tests

- Crash after commit before broadcast, then resume: events committed with no broadcast, engine closed and booted again on the same file, client resumes with `Last-Event-ID` and gets them, then live ones.
- 100 disconnect cycles under live ingest (events before, during, and after each connection; 1 to 3 frames read per connection): the received IDs are exactly 2..301, no gaps and no duplicates.
- Slow consumer: with a 50-frame queue, one subscriber that never reads is cut off with `slow_consumer` after a contiguous prefix, while the other receives all 201 events and keeps streaming. The default queue is 1,000.
- A real-socket test: `fetch` with `X-Taskville-Session` streams frames through `@hono/node-server`, and aborting the fetch removes the subscriber.

## Lessons

- Hono's `writeSSE` awaits before it hands the frame to the writer, so `writeSSE(frame)` followed by `close()` without awaiting closes first and silently drops the frame (Hono's `write` swallows the error). `stream.write(text)` hands the bytes over synchronously and keeps the order.
- Hono streams apply backpressure: with nobody reading, only one `writeSSE` resolves. That is what makes a bounded per-subscriber queue meaningful; the frames back up in our queue, not in Hono.
- Two mutations survived the done-when tests (dropping duplicates, paging the backlog) because the paths they guard are unreachable in a normal run. Tests that publish an old batch again and stream a 600-event backlog with nothing live now pin them.
