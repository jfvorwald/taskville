- **Root cause:** CI runs on ubuntu-26.04, whose `/usr/bin/mkdir` is Rust uutils coreutils 0.8.0. It checks whether the path exists and then creates it; if the directory appears in between, it exits 0 although the kernel refused (upstream uutils issue #13970, fixed in 0.11.0). The shim's `claude-code.lock` relied on `mkdir` failing for an existing directory, so two shims could both hold the lock and append together; one shim's torn-line repair then added a stray newline, leaving an empty line that `JSON.parse` rejects.
- **Fix:** a shim holds `claude-code.lock` only once it has also created the lock's `pid` file with `set -C` (an exclusive create in dash and bash); the break lock works the same way; release removes only our own `pid` file and then the directory if empty. The directory-plus-pid layout shared with the engine is unchanged. The engine (`apps/engine/src/sources/claude-code/spool.ts`) now follows the same rule: `takeLock` fails when its exclusive `pid` create fails (a shim that won that race holds the lock, so a replay can no longer rename the main file under a shim's append); its break lock is pid-owned the same way; release removes only its own `pid` and then the directory if empty. Tests use a real paused shim with a uutils-like `mkdir` on PATH and `node:fs` seams for the release race.
- **Lessons:** `mkdir` is only a safe lock if the `mkdir` command is atomic, and uutils 0.8.0 is not; confirm ownership with something only one process can create. When the same flake recurs after a fix, collect every CI failure message first: identical messages pointed to a fixed corruption shape, and the runner image explained why it only happened on Linux. Investigation by the debugger.
