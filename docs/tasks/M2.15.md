## What changed

- `reducer/attention/requests.ts`: the "one prompt, one red state" merge target, which feeds `stateHash`, picks the earliest request with `compareTimestamps` (exact, offset-aware) instead of `Date.parse`.
- `selectors/attention.ts`: records sort by `compareTimestamps` on `since`, and quiet time uses a new `epochMillis` (exact to the millisecond, no `Date`).
- `reducer/entities/time.ts` (outside Owns, forced, small): `epochMillis`.
- `test/purity.test.ts` (forced): the domain bans `Date` entirely, `Date.parse` and `Date.UTC` included. Nothing in `packages/domain/src` uses it any more.
- `REDUCER_VERSION` 4. #197 took version 3, and this change alters which record a request merges into for timestamps that tie at the millisecond, so stored projections must be rebuilt. The pinned hash prefixes in the CLI and demo tests and the two domain snapshots are updated (only the version field changed).
- Tests: `test/attention/ordering.test.ts` covers sub-millisecond, nine-digit, and offset timestamps whose ID order is the opposite of their time order, for both the merge target and the attention sort.

## For the lead

- `apps/cli/src/status.ts` (`highest`) still orders attention records by `since.localeCompare`, which is text order, not time order, once offsets differ. It affects only which record a `status` line shows, not state. It is outside this ticket's Owns; a one-line follow-up could switch it to `compareTimestamps`.
- Real Claude Code timestamps come from the engine clock (millisecond precision, `Z`), so the old tie never fired on recorded traffic. The fix matters for other producers and for history imports.
