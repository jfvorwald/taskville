- **Lessons:**
  - The test reader `SseReader` (`apps/engine/test/stream/helpers.ts`) leaves a `read()` pending after a timed-out `next()`, and that read swallows the next chunk. `expectQuiet` followed by live frames only works if something is written during the quiet window, so the feed sends a heartbeat (`{ head }`) once its backlog is sent. The one test that pins the opposite (a revoked browser feed must read `null` with nothing sent) only passes because the heartbeat waits a turn of the event loop and the stream is already aborted by then. That pair of tests is timing sensitive; a test-writer should fix the reader.
  - A frame must be built at write time, not at queue time, for anything the producer fills in after commit: the Claude Code source stores evidence bodies right after its events commit, so a status read in `offer` would race it.
  - A pin that stops a recording "before the SessionEnd" is not a pin on the session boundary: the reducer also closes an unregistered helper's calls at the lead's turn end (`Stop`), which is earlier. When a test depends on a domain rule, derive the stopping point from the reducer's rule, not from the name of the hook.

## What changed

Owns (`apps/engine/src/feed/`, all new):

- `index.ts`: exports (`registerFeedRoutes`, `FeedRouteOptions`, response types).
- `routes.ts`: `registerFeedRoutes` and the feed and crew routes. The feed follows the attention route: `read` scope, the stream cap, `hub.track` for shutdown, `pairing.onRevoke` for browser sessions, and the cursor rules of the project stream (`Last-Event-ID` wins, malformed is `400 bad_request`, past the head is `resnapshot` / `cursor_ahead_of_head`, with the write raced against the drain timeout).
- `subscriber.ts`: `FeedSubscriber` (backlog from storage, then live from the hub, no gap or duplicate; queue of `queueLimit` frames, overflow is `resnapshot` / `slow_consumer`; every write raced against the drain timeout) and `writeWithin`.
- `tool-calls.ts`: `ToolCallTracker`, the per-agent fold of `tool_call.*` events into ToolCalls with the reducer's rules but no cap (the projection keeps only a bounded set). Round 2: it takes `(projectId, agentId)` and every event of the project, runs the domain `reduce` beside its fold, and when the reducer marks one of the agent's open calls `unfinished` it emits that call with `phase: "unfinished"`, `finishedAt` of the boundary event, no `durationMs`. A later `tool_call.finished` replaces `unfinished`, as in the reducer.
- `agents.ts`: `resolveAgentProject` (404 `unknown_agent` / `unknown_project`, 409 `ambiguous_agent`).
- `crew.ts`: `buildCrew` from the stored projection (or a replay), plus finish summaries from `agent.finished` events.
- `evidence.ts`: an `unfinished` frame has no output evidence (round 2); evidence IDs (base64url of a JSON `[projectId, toolCallId, part]`, strictly re-encoded on read so one body has one ID), frame references, and `GET /v1/evidence/:id` (404 `unknown_evidence`, 410 `evidence_evicted`, masks from the `[REDACTED:kind]` markers of a body the redactor changed).

## Decisions taken inside the ticket (flagged for review)

- The frame carries `toolName` only when the call's start was recorded (the reducer's rule); the pinned shape lists it as required.
- A running frame shows `evidence.input` but never `evidence.output`, even if the output is stored by the time the frame is written; a finished frame shows both. Status (`stored` / `evicted`) is the store's at write time.
- Crew members' `heuristic` is `false` for every member, because a member is listed only on a recorded link and recorded fields are never overwritten by a guess. `currentActivity` is present only for a running member with a known activity.
- A heartbeat `{ head }` is sent once the backlog is sent (see Lessons).
- A repeated start or finish sends no frame.
