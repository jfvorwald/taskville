## What the crew mapper does

`packages/adapters/src/claude-code/crew/` exports `mapCrewHook(payload, ctx)` (same context and `{ events, ignored? }` shape as the core mapper) and `attributeHook(payload)`, which says which agent any hook belongs to and whether it is a session, subagent, in-process teammate, or internal helper. Agent IDs, `sourceAgentId` values and ID bounds match the core mapper on the M2.03 branch (`claude-code:<session_id>` and `claude-code:<session_id>:<agent_id>`).

| Hook | Events |
| --- | --- |
| `SubagentStart` (subagent) | `agent.registered` kind `subagent`, no parent (S-2: the hook has none) |
| `SubagentStart` (in-process teammate, every turn) | nothing |
| `PostToolUse(Agent)` with `agentId` | `agent.registered` for the child with `parentAgentId` = the caller. This is the recorded parent link, nested subagents included |
| `PostToolUse(Agent)` `teammate_spawned` | `team.started`, the caller registered as `lead` (same name as core's SessionStart), and for in-process mode the teammate registered with its team. Split-pane spawns register no teammate: that `agent_id` never shows up in the teammate's hooks |
| `SubagentStop` | subagent: `agent.finished` with the masked last message as summary. In-process teammate: `activity.ended` (idle, #120 D3) |
| `TeammateIdle` | `agent.registered` kind `teammate` with `teamId` (recorded link, both modes), then `activity.ended` |
| `PostToolUse(SendMessage)` that succeeded | `team.message` from the caller (`to`, `kind`, masked `summary`, no body). For a session sender (split-pane), also a `heuristic: true` teammate registration named from `routing.sender`, with no team |
| `Notification` `worker_permission_prompt` | `request.opened` on the lead, `reason` "for: pip (Bash)", `heuristic: true`, never answerable |
| `TaskCreated` / `TaskCompleted` | `task.created` / `task.status_changed completed`, task scoped by team |
| Internal helpers (agent_id, empty `agent_type`) | nothing |

How history-dependent links are handled: the pure mapper emits facts and relies on the reducer's existing rule that a registration that omits a link keeps the recorded one. That is why a SubagentStart (no parent) can arrive after the parent's Post (with parent) without losing the link. The only guessed link (split-pane name from `routing.sender`) and the only guessed attribution (the worker prompt on the lead) carry `heuristic: true`, as #120 requires. A later strict mode has to treat a recorded registration as winning over a later heuristic one, because the mapper re-emits the heuristic link on every SendMessage from that session.

## Follow-ups for the lead

- Wiring: once #22 merges, `claude-code/index.ts` should run both mappers and concatenate events (core first), and crew should import core's ID helpers instead of mirroring them. Pending in this PR if #22 is not merged first.
- Split-pane teammates: core maps their `Stop` to `session.turn_ended` (waiting on you). A teammate turn ending is idle, not waiting. Consider suppressing that attention for sessions registered as teammates (reducer or M5).
- The in-process teammate test relies on the `a<name>-<16 hex>` agent_id shape. If Claude Code changes it, teammates become subagents and finish on their first idle. The fixtures pin the shape.

- Heuristic marker in state (the roborev high, fixed with the lead's approval). In `packages/domain`, a heuristic `agent.registered` only sets `Agent.heuristic { displayName, kind }`. It never changes the recorded name, kind, identity or links, whichever arrives first, and a recorded registration clears it. `PendingRequest.heuristic` flows into `needs_you` attention. Two worker prompts never merge. A worker prompt that arrives after the lead's generic `permission_prompt` takes over that record, so its "for: <name>" survives either order (this answers the async race noted above). `REDUCER_VERSION` is now 2; the two state snapshots changed only in that field, and the tests that hard-code a `1:` hash prefix were updated. In `apps/cli/src/status.ts` and `cli.md`, a guess shows as `maybe pip (teammate, heuristic)` and a guessed request as `needs you (heuristic): ...`.
- A worker prompt stays red on the lead until the lead's next event (roborev 5135, answered). That is the documented closure rule (ARCHITECTURE.md 8.1, events.md), and core's `permission_prompt` request behaves the same. In the split-pane stream, the lead's Stop closes it 16 hooks later. Closing it from the teammate's session would need a guessed cross-session link. A future improvement: once a teammate is linked by a recorded TeammateIdle, the reducer could close the lead's worker requests on that teammate's next tool call.

## Lessons

- The reducer ignores a second `agent.registered` that claims an agent ID under a different `sourceAgentId`. Two mappers that register the same agent have to agree on `sourceAgentId`, not just the envelope `agentId`. I caught it only by reading the other branch.
- Emitting a heuristic marker is only half the job. If the projection drops it, the guess shows as a fact. The domain and presentation changes should be scoped into the ticket that adds the marker.
- The reducer's request merge keys on tool name. Leaving out a field the other mapper never sets (`toolName`) is what merges two notifications about one prompt into one red state.
