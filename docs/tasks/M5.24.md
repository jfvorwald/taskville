## Debug round (stopped: guard test conflicts with the per-window budget)

Debugger, assigned after the finding survived two fix attempts. No source change committed; HEAD source is unchanged from 385ba71.

Reproduced at 385ba71: ConnectedPrivacySearch browser file, 23 tests, 2 fail (Grep and Glob `keeps loading a new group at the tail after 90 standalone calls stream past`), 21 pass.

Root cause of the red tests (confirmed by a temporary `console.log` probe in `visibleReader`, since removed): `claimed` adds every stored id of every call that was ever visible and is only reset on resnapshot. After the 90 Bash calls every report reads `claimed=180 granted=0 outputOnly=2 allowed=0` while only 8 or 9 calls are visible (16 to 18 bodies). The new group's 2 outputs are filtered out of `allowed`, so they never enter `wanted` and are never fetched.

Candidate fix tried (attempt 1, reverted): build `claimed` and `granted` from the current report only (locals inside `visibleReader`, resnapshot resets removed), so the budget is the current window's: 5 lines in `ConnectedLiveTab.tsx`. Result: 21 pass, both tail tests pass, refetch-after-scroll-back and no-thrash guards pass. But Grep and Glob `requests no more bodies for a static window than the cache holds` fail with `expected 130 to be less than or equal to 122`, the same number green round 4's first attempt hit.

Why that guard fails under any per-window budget (probe of every report and every fetch in that test):

- The mount does not stay on one window. The first reports are at the top (`cs-bash-1..3`, `cs-write-0,1`; outputs 1 to 96 offered), and the 6 Bash bodies are fetched there. Follow then moves to the tail and alternates between two settled windows: G2 to G5 (outputs 33 to 152 allowed, 120, because 4 divider Writes each reserve 2 in `privacyOutputs`) and G3 to G5 (outputs 65 to 160, 96).
- Each single window fits the cache (6 + 96 at the top, 0 + 120 at the tail). No id is fetched twice. No body was evicted while its key stayed wanted (separate probe, all 23 tests).
- The tail windows alone union to outputs 33 to 160 = 128 distinct search outputs, plus 2 of G1 from the top transient = 130. The bound is `CACHE - standalone().size` = 128 - 6 = 122, where the 6 Bash fetches come from the transient window and are not in the settled one.

So the guard's premise ("the view is static, so everything fetched is the current window") does not hold for this fixture. It measures distinct fetches accumulated across windows, which is the dropped cumulative bound under a new name. An implementation that keeps every window within the cache and loads a new tail group after 90 standalone calls cannot also keep the union of this mount's windows at 122 or below: the union is 128 even with zero transient G1 fetches. Only a ledger that never releases (ce651c1) passes this guard, and that ledger is exactly what fails the tail test. Rules that pass both (for example not evicting earlier search outputs for new ones) pass only by a 0-margin coincidence that depends on how many G1 fetches race in the transient, and they reintroduce the same "visible group never loads" class.

Not needed by any test: clearing `requested` on eviction. LiveFeed reads every visible body on each render, so bodies that stay visible stay most recently used, and the eviction probe never fired. It remains a theoretical case (cached but unallocated group outputs that are also touched on render could crowd the LRU). It is not verified either way.

Side note: `privacyOutputs` counts body-less standalone calls (the divider Writes) as 2 bodies each. This over-reserves and is safe.

Decision needed from the lead (test-writer change, not a debugger edit): restate the static-window guard so it measures one settled window, for example snapshot `hits` once the view has settled and assert no further fetches over the next interval (the no-thrash test already bounds per-id counts), or use a fixture whose settled window contains the standalone calls it subtracts. With the guard restated, the 5-line per-window ledger above is the proposed fix; it passed every other test in the file.

Checks: ConnectedPrivacySearch browser file run 3 times in total (baseline at HEAD; candidate with probe; probe-only filtered to the guard). Nothing else run.
