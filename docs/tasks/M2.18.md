## What changed

1. **Projection kept in memory between batches** (`apps/engine/src/ingest/pipeline.ts`).
   - **Cache contents:** the pipeline keeps each project's state as it committed it, with its head, reducer version and stateHash, updated only after COMMIT.
   - **When it is used:** a batch uses the cached state only while the stored row still has the same head, reducer version and stateHash. Those three columns are read with the new `projectionMeta`, which does not read or parse `state_json`.
   - **Invalidation:** another connection's events (head moved) or projection rewrite (a rebuild at the same head: hash changed) make it read from disk again, as does a new pipeline (a restart).
   - **Purity:** the cache relies on the reducer being pure (constitution III). The equivalence test runs the domain reducer with every state deep-frozen, so a mutation would throw.
2. **One serialization per projection write** (`apps/engine/src/storage/storage.ts`). `writeProjection` called `stateHash` (canonical JSON, then SHA-256) and then `canonicalJson` again for `state_json`. It now serializes once and hashes the stored text. A test checks the result against `stateHash`, and the reducer-version check matches the one `stateHash` makes.
3. **Explicit SQLite memory and WAL settings** in `openStorage`: `cache_size = -2048` (2 MiB; SQLite's default is about 2,000 KiB, now explicit), `wal_autocheckpoint = 1000` (the default, explicit), and `journal_size_limit = 4 MiB`, so the `-wal` file is cut back after checkpoints instead of keeping its largest size.
4. **The soak reports the `-wal` size** at every hour mark (`tests/perf/soak.ts`, `run.ts`; a forced extra path).

## What this means

- **Noise, not growth.** Within one run, calm RSS swings 30 to 45 MiB from hour to hour, without a trend. Across the three runs, hour 1 alone ranged from 102.6 to 125.5 MiB and hour 8 from 132.0 to 153.5 MiB. The 10% target is about 11 to 12 MiB, smaller than the run-to-run spread of a single sample. Which one moment `ps` lands on decides the verdict.
- **How much tracks projection size (for #167).** Very little. Calm state grows by 121 KiB of JSON over 8 hours (27.0 to 148.3 KiB). Even at several times that in parsed objects, it is well under 1 MiB, against an hour-1-to-8 RSS difference of 17.6 to 31.1 MiB in these runs. Lively grows its state about 7× (64.7 to 474.3 KiB), and its RSS ended lower than at hour 1 in all three runs.
  - Pruning projection state (#167) is worth doing for the snapshot size and replay cost.
  - On its own it will not bring SC-006 under 10% as measured. Most of the gap is allocator and V8 page retention, consistent with #166's flat-heap diagnostic.

## Lessons

- Two engines fed the same events produce different stateHashes, because engine-assigned event IDs are in the state. An equivalence test across databases needs deterministic `newEventId`s. My first version failed on that, not on the cache.
- A perf baseline taken from a worktree that is being edited is only valid if the spawned engines started before the first source edit. Check the timestamps, or measure from a clean checkout.
- A metric whose run-to-run spread is larger than its threshold cannot be passed by fixing the code: three runs gave 14.0% to 28.7% on the same code.
