### Design note for the implementer (my decision; the tests do not depend on names)

- Where: a new additive migration `V3` in `apps/engine/src/storage/migrations.ts` (append to `MIGRATIONS`; never edit V1 or V2; `LATEST_SCHEMA_VERSION` becomes 3, and `test/storage/open.test.ts` derives its expectation from it).
- Shape: `agent_events (project_id TEXT NOT NULL REFERENCES projects(id), agent_id TEXT NOT NULL, ingest_sequence INTEGER NOT NULL, PRIMARY KEY (project_id, agent_id, ingest_sequence)) STRICT, WITHOUT ROWID`, plus a lookup by agent across projects (`agent_id` first, for resolution: "which projects hold this agent" is `SELECT DISTINCT project_id ... WHERE agent_id = ?`, O(log n) and O(1) for a miss).
- Maintenance: an `AFTER INSERT ON events` trigger (so it holds for every connection, like the existing triggers) inserting a row when the envelope has an agent id (`json_extract(NEW.envelope_json, '$.agentId')`). The same migration backfills existing databases with one `INSERT ... SELECT` over `events`. A migration backfill test (build a database at V2, open it, assert the lookups still find old events) is not in this red set because V1 and V2 are not exported; add one when implementing.
- Reads: `Storage` gets a method that yields a project's events for one agent (and whatever the tracker needs, see below) in sequence order; `holdsAgent` becomes an index lookup; `buildCrew` reads summaries and the state of the crew without a whole-log pass.
- Open question for the implementer, not decided here: the feed tracker must still apply events of other agents that can close this agent's calls (a session owner's boundary closes an unregistered helper's calls; `agent.registered` links). The bound of 40 rows leaves room for the target's own events plus its session's events, not the project's. If that cannot be done without a session index, add `session_id` to the index and report it; do not raise the bound.
- Keep the M5.15 frame scheme (`id` only on the last frame of an event) and the M5.15 closure rule (`callsClosedAtBoundary`) as they are. The guard for the lookup: return no closures, without calling `reduceEntities`, when `toolCalls` is unchanged by the event.

Table `agent_events (project_id, agent_id, ingest_sequence, session_id, type)`, primary key `(project_id, agent_id, ingest_sequence)`, `STRICT, WITHOUT ROWID`; indexes by `(project_id, session_id, ingest_sequence)` and `(project_id, type, agent_id, ingest_sequence)`; an `AFTER INSERT ON events` trigger (only events that name an agent); one `INSERT ... - `feed/agents.ts`: `holdsAgent` keeps the projection fast-yes, then asks the index (no log read; a miss is one lookup per project).
- `feed/crew.ts`: finish summaries come from `agentEventsOfType(..., "agent.finished")` per member, so no pass over the log when the projection is current (a stale projection still replays).
- `feed/subscriber.ts`: backlog reads `agentFeedEvents`; after the last page `lastQueued` jumps to the head read in the same tick, so live gap detection is unchanged.
- `feed/tool-calls.ts`: closure guard, no `reduceEntities` when the event left `toolCalls` the same reference.

Design finding (reported, as asked): the feed needs more than the agent's own events. `agentFeedEvents` returns (1) the agent's events, (2) every event in a session the agent has events in (a session owner's boundary closes an unregistered helper's calls, M5.15; ownership is decided by who named the session first), (3) `agent.registered` events of agents seen in those sessions (a subagent never owns a session). That is why the index carries `session_id` and `type`. The red-test bounds were not raised.

## Debug round

Assigned by the lead after roborev 6880, post-commit 6873 and a code review: the subset fold diverged from a full fold. Reproduced first: `subset-fold.test.ts` 3 failed (cases 1, 2, 3), 3 passed.

Root cause, two parts, each confirmed with a throwaway storage probe (outside the repo) before any change:

- Cases 1 and 2 (query). `agentFeedEvents` returned registrations only for agents seen in the agent's sessions, and no other agent's `agent.finished`. Probe: case 1's helper subset held 1 of the 56 finishes, so the tracker's reducer never had more than 50 finished agents, retention never dropped the helper (case 1) or the old owner and its session (case 2), and the subset state kept a registration and an owner the full fold had dropped.
- Case 3 (cursor). The tracker folds a session's events only from the cursor at which the session joined the agent's session set. Probe: after the agent entered `c3-s2`, the read at `after=3` returned sequences 4 and 5 while the same query from 0 returned 1 to 5; the owner's `session.started` (1) was never folded, so the intruder named the session first in the subset state, owned it, and its turn end closed the call. The same mechanism hits the live path with no missed broadcast at all (probe: a live feed sent `t1:unfinished`, the full fold `t1:running`) and a session entered between backlog pages. Not covered by a committed test (debuggers do not edit tests); a follow-up test is suggested below.

Fix (`apps/engine/src/storage/storage.ts`, `apps/engine/src/feed/subscriber.ts`):

- Query: (a) the agent's own events, (b) every event of its sessions (whole log), (c) and (d) every `agent.registered` and `agent.finished` of the project (by the type index). The mates-only registration clause is gone (subsumed).
- `Storage.agentSessions(project, agent)`: the agent's sessions, each with its first indexed sequence.
- Subscriber: it reads the session set at its first read and again only after it meets the agent in a session the set does not cover (live: the event is not applied and the feed goes back to storage; a page: it stops before that event). If a new session has an event at or below the fold cursor, the tracker starts over from sequence 1 on the current subset, and only frames above what was already sent go out (`#quiet`, which starts at `after`). A new session whose first event is the one just seen needs no restart.

Mutation (by hand, restored, nothing committed): with the restart disabled, case 3 fails and the other five pass.

Retention does depend on more: its kept set reads unended teams (their lead), open requests (their agent) and every agent's running calls, for the agent and for the owners of its sessions. Performance finding, not fixed (outside this correctness round): the `sessions` CTE of `agentFeedEvents` (and `agentSessions`) is planned on `agent_events_by_session` as `project_id=? AND session_id>?` because of `session_id IS NOT NULL`, which scans every indexed session row of the project, about 2 to 3 ms per call and so per 256-event page. Without that term the planner seeks the primary key (0.009 ms for a subagent). `session_id IN (...)` never matches a NULL, so dropping the term from the CTE is equivalent.
