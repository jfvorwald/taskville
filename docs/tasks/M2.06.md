## Write path (`prepareBody`)

1. **Serialize.** A string (a Bash `tool_response`, say) is kept as is. For anything else, the whole value of every sensitive key (`password`, `apiKey`, `token`, ...) of any non-null, non-string type is first replaced by the `sensitive-value` marker: `redactJson` masks only strings directly under such a key, so `{ password: { value } }`, `{ apiKey: [{ k }] }` and `{ token: 123 }` passed (roborev 5142). Whether a key is sensitive is asked of `redactJson` itself with a probe value, so there is no second list to drift (L-17). Then every string is masked with `redactJson`, which keeps a `__proto__` key as data (L-18), and the result is written as compact JSON.
2. **Well-formed.** `toWellFormed()` turns a lone surrogate into U+FFFD (L-31), so the hash covers exactly the bytes SQLite stores.
3. **Mask the whole text** with `redactText`. It runs on the full body before any cut: cutting first can split a secret, or a private key block, so the redactor no longer recognizes the half that is kept. There is deliberately no pre-cut for speed; the route's 5 MB limit bounds the work.
4. **Cut to 64 KB after masking** (L-32): 65,536 UTF-8 bytes including `TRUNCATION_MARKER`, on a character boundary.
5. **Hash the stored bytes** (SHA-256). The key is the hash of redacted bytes, so nothing stored is derived from the raw body.

A value that cannot be serialized (a BigInt, or nesting deep enough to overflow the stack) is skipped and logged by error name only; the other parts of the call are still stored.

## Schema (`evidence.db`, `user_version` 1)

- `bodies (project_id, hash, body, bytes, truncated, masked, last_used)`, primary key `(project_id, hash)`: content-addressed per project, so the per-project cap and project deletion are single-project queries. Identical content is stored once per project.
- `tool_call_bodies (project_id, tool_call_id, part, hash, stored_at)`, primary key `(project_id, tool_call_id, part)`: the ToolCall pointer. Never evicted. The first body for a part wins, like the event log's first write, so a duplicate delivery stores nothing new.
- `usage (project_id, bodies, bytes)`: kept in the same transaction as every insert and eviction, so the cap check reads one row instead of summing up to 1 GB of rows.

The file and any `-wal`/`-shm` are created or tightened to 0600 with `O_NOFOLLOW` before SQLite opens them (`secureDatabaseFiles`, L-23), in WAL mode with `synchronous=NORMAL` and defensive mode. A newer `user_version` is refused.

## Eviction

Over the cap, the project's least recently written bodies go first; storing or re-referencing a body makes it the newest. The body just written is never evicted, even when it alone is over a (tiny) cap. Pointers stay, so `get` reports `evicted` with "details no longer stored"; if the same content arrives again, it is stored again and old pointers resolve once more. `last_used` ticks come from the engine process, so one engine per file.

## Tool call IDs

Stored unmasked (they are IDs), so the store accepts only a string of 1 to 200 characters, well-formed, without control characters, that the redactor would not mask. Others are skipped.

## Follow-up for the lead

- **Ingest has the same nested gap.** `redactJson` masks only strings directly under a sensitive key, so an event payload such as `{ "password": { "value": "x" } }` keeps `x` at ingest too (M1.20 module, `packages/adapters/src/redact`). Evidence is covered by the pre-pass here. Fixing `redactJson` itself changes masking, and so the dedupe hashes of events ingested before the fix (a retried old event would become a conflict), so it is worth its own ticket rather than a change inside this one.

## Lessons

- The tempting optimization (cut huge bodies before masking) is a leak: a private key block cut in half is no longer a recognizable block. Masking the whole body first and cutting after is the only safe order, and the test for it is a key block longer than the cap.
- Evidence must be bound to the hook that was recorded, not to its key. Events omit the bodies, so a retry that matches as a duplicate, or a hook where one event conflicts and another is new, can carry bodies that were never part of the recorded hook. Two review rounds found this one case at a time; "every event accepted" closes the class.
- A per-project usage row maintained in the same transaction keeps the cap check O(1) without trusting an in-memory counter.
