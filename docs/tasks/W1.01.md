# W1.01: Web performance below the ARCHITECTURE section 11 budget (33 fps moving, 8% idle CPU) (#268)

- **Result:** done (investigation; no source changed). The moving shortfall has one cause, confirmed by experiment: the render pacer and R3F's demand loop hand off one display frame late, so the city draws every other frame. Idle CPU is spread across three costs, and no single fix brings it under 5%.
- **PR:** none (profile commit on W1.01, not pushed) · **roborev:** not run (docs-only commit; the lead decides whether this report needs a PR)
- **Checks run:** `node tests/e2e/web/measure.ts --headed --moving 10 --settle 8 --idle 10 --port 4887` on the production build, twice (load given below). Breaks e2e once (`VITE_TV_TEST_HOOKS=1 vite build`, then `E2E_PORT=4939 pnpm exec node e2e/run.ts e2e/breaks.spec.ts` in apps/web, temp HOME): 1 passed in 5.5 min, `IDLE_FPS 20.3 (203 frames in 10.0 s, 4 agents on break, headless SwiftShader)`. Plus throwaway profiling runs (CDP traces, V8 CPU profiles, per-tick draw and React commit counters, per-process CPU), outside the repo in /tmp, not committed.
- **NOT RUN:** `pnpm check` (docs-only change, and biome does not cover markdown); `tests/perf` (engine ingest and SSE latency, not web rendering); the full e2e suite (push tier); headed runs on a reserved machine (none was available, see Environment).
- **Measurements:** see "Current numbers" and "Ranked costs" below.
- **Decisions needed:** one proposed, not opened: the idle frame budget (ticket E below). The lead opens it if the owner's call is needed.
- **Review outcome:** not reviewed yet
- **Lessons:**
  - A pacer that decides in its own requestAnimationFrame callback and then calls R3F's `invalidate()` draws at half rate. R3F starts its demand loop with a new requestAnimationFrame, which lands one display frame later, behind the pacer's own callback. Unit tests of the pacer logic cannot see this. Only a test that counts real renders per animation frame catches it.
  - To split idle CPU into parts, change one thing at a time in the same page: an empty scene, then no draws, then no requestAnimationFrame loop. Per-process CPU from CDP `SystemInfo.getProcessInfo` turns that into numbers without touching source.
  - A measurement that moves the mouse right before an idle window measures one second of full rate. Any input event holds the throttle at full rate for 1 s.

## Ranked costs

### 1. Pacer to R3F handoff halves the moving frame rate (moving: 33 fps instead of 60)

- **Symptom:** requestAnimationFrame runs at 60.0/s, but the scene draws 33.2 times a second. The per-tick draw pattern is `1010110101...`: of 265 gaps between drawn ticks, 211 are two ticks and 52 are one tick. The one-tick gaps are extra frames started by React commits.
- **Not a work limit:** trace of the moving window at 33 fps: renderer main thread busy 14.1% of wall time, GPU process main 6.8%, renderer compositor 2.8%, viz 2.5%. JS on the main thread was 369 ms in 6.1 s.
- **Mechanism** (`@react-three/fiber` 9.8.2, `dist/events-e51d7528.esm.js` lines 17548 to 17610, `loop` and `invalidate`). `RenderPacer` requests its next frame at the top of its callback. When it decides to draw, it calls `invalidate()`, which sets `frames = 1` and, because R3F's loop is stopped, calls `requestAnimationFrame(loop)`. That puts R3F's loop one display frame later, behind the pacer. On that next frame the pacer runs first and calls `invalidate()` again. `frames` is already 1 and the loop is marked running, so the call merges into the pending frame. R3F's loop then draws, drops `frames` to 0, and stops. On the frame after that, the pacer has to start the loop again, and it draws one frame later still. The result is one draw every other display frame.
- **Experiments** (same harness and conditions; source not changed):
  - Emulated fix: an init script defers the pacer's own `requestAnimationFrame` call to a microtask, so it is requested after `invalidate()` and R3F's loop runs first on the next display frame. Moving reached **59.7 fps** (load 33), 59.5 (load 20, with profiling on), 59.9 (deviceScaleFactor 2, load 6) and 59.7 (deviceScaleFactor 2, load 20).
  - R3F `frameloop` set to `"always"`: 60.1 fps.
  - At 60 fps (emulated fix, deviceScaleFactor 1): renderer main thread busy 26.8%, about 4.5 ms of each 16.7 ms frame. GPU process main 14.5%. Browser CPU 30 to 37% of one core, and 38.8% at deviceScaleFactor 2.
- **Proposed fix** (small and contained, but source, so not committed). In `apps/web/src/city/runtime/RenderPacer.tsx` `loop`, call `invalidate()` first and only then request the next animation frame. Use `try/finally` so that a throw still re-arms the loop:

  ```ts
  const loop = (t: number) => {
    try {
      // ...camera and motion signals as today...
      if (pacer.shouldRender(throttle.update(signals), t)) invalidate();
    } finally {
      // After invalidate(): R3F's demand loop then runs ahead of this callback on the next
      // display frame, so a requested draw lands every frame instead of every other one.
      raf = requestAnimationFrame(loop);
    }
  };
  ```

  A sturdier alternative is to stop depending on callback order: use `frameloop="never"` and call R3F's `advance(t / 1000)` from the pacer when it decides to draw. That is a larger change, because commit-driven redraws (`invalidateInstance`) stop and the pacer becomes the only driver. The test below should decide between the two.
- **Watch:** two of the six emulated-fix runs read idle at 34.4 and 38.6 fps. Two later reruns with every `invalidate()` call traced did not reproduce it. In those runs the pacer was the only caller (128 to 130 calls in 180 ticks), React commits and `useFrame` made none, and idle settled at 20 fps after the one-second artifact. The real desktop pointer may have been over the headed window. The ticket's Done when therefore also checks the idle rate.

### 2. Each idle frame costs about 1.5 ms of CPU even with an empty scene (idle: about 3.0 points, 44% of idle CPU)

Idle CPU split by removing one thing at a time in the same page, headed, deviceScaleFactor 1. The measurement's own requestAnimationFrame counter was stopped. Frames were counted from WebGL `clear` calls. Load 22.

| Variant (10 s each) | Frames/s | Browser CPU (renderer + GPU + browser) | Difference |
|---|---|---|---|
| Product as built | 20.1 | 6.84% (3.34 + 3.43 + 0.05) | |
| Empty scene (`scene.visible = false`, still clears and presents 20 frames/s) | 20.1 | 5.14% | scene content 1.70 |
| No draws (`frameloop "never"`, pacer still polls at 60 Hz) | 0 | 2.15% | present 2.99 |
| No requestAnimationFrame at all (pacer stopped too) | 0 | 0.22% | 60 Hz polling 1.93, floor 0.22 |

- Repeats at other loads agree: product 8.07, no draws 2.83, no rAF 0.14 (load 27); product 6.38, empty 5.39, no draws 2.06 (load 25).
- WebGL context attributes are not a lever. `alpha: false` read 6.38% and `antialias: false` read 11.2%, against 6.84% for the default. Both are within noise or worse.
- What still draws: the whole scene, 121 draw calls and 2,766 triangles per frame, 20 frames a second. Only the pacer requests these frames. The frames do change: in the idle window, 5 agents were working (work-pose loop) and 1 was stuck on Needs you (attention pulse). The 20 fps redraw is the behaviour ARCHITECTURE section 11 specifies.
- JS per idle frame is 0.36 ms (R3F loop 75.9 ms over about 210 frames). Of that, three.js `render` is 0.31 ms, with `setProgram` and uniform uploads making up about half. Trace: renderer main thread busy 4.7%, GPU process main 3.4%.
- The only lever here is fewer idle frames. See ticket E.

### 3. The pacer polls at 60 Hz while idle (idle: 1.9 to 2.7 points, 28 to 33% of idle CPU)

- In the idle trace, the renderer runs `ProxyMain::BeginMainFrame` 60.0/s, `Commit` 60.0/s and `PrePaint` 60.0/s, but only 20 frames a second draw. FireAnimationFrame runs 140/s (the pacer plus the measurement counter). The pacer's own JS is cheap (16 microseconds per tick). The cost comes from the Blink frame lifecycle that each requested animation frame triggers.
- Measured cost: 1.93 to 2.69 points (no-draws variant minus no-rAF variant, table above).

### 4. Draw calls per frame: 121, half of them static city meshes (idle: 1.0 to 1.7 points; moving: about 2% of the main thread)

- Drawables per frame (headless count, demo city): city 58 meshes, 10 instanced meshes and 1 sprite; agents 50 meshes and 2 sprites (about 8 per agent). The scene has 219 objects, all with `matrixAutoUpdate` on.
- The 58 city meshes are building parts (`city/buildings/Buildings.tsx`: one mesh per box, shared unit geometry, a few tone materials) and ground parts. Buildings support hover and per-building fade (`InteractionLayer`), so merging them needs a design check.
- Moving at 60 fps: three.js render is 133 ms of the 228 ms R3F loop in 6.1 s, about 2.2% of main-thread wall time. App `useFrame` code (CityAgents, navigator, AgentBlock, crew, attention marks) is about 27 ms.

### 5. React DOM work while moving (moving only; not limiting)

- At 60 fps (emulated fix): 94 react-dom commits per second (1.6 per frame), plus 15.1 per second on the R3F reconciler. React work was 226 ms in 6.1 s, which is 3.7% of main-thread wall time and 40% of JS: react-dom 83 ms, react-aria and react-aria-components 93 ms, `getBoundingClientRect` 5.6 ms.
- Two drivers. First, the 120x demo's event rate re-renders `OverlayRoot` through `useData((s) => s.state?.agents)`, and its deps-less `useLayoutEffect` calls `placeSidebar` (forced layout) on every render. Second, the per-frame anchor bumps (`publishPositions` calling `setAnchor`) re-render both AnchorLayers (labels and bubbles).
- At 33 fps the share is about the same (performWorkOnRoot 186 ms in 6.1 s). With the main thread at 27% busy at 60 fps, this is headroom, not a bottleneck. Low priority.

### Measurement findings (tests/e2e/web/measure.ts)

- **M1:** `parkPointer()` runs right before the idle window. Playwright's `mouse.move` fires `pointermove`, `RenderPacer` sees `touched`, and the throttle holds full rate for 1 s. Every idle window therefore starts with about 62 ticks at the full-rate cadence before it drops to every third tick (per-tick pattern recorded). Today this lifts idle from 20.0 to 21.0-21.2 fps. With the pacer fixed it reads 24.2 to 25.4 (observed with the emulated fix) and adds about a point of CPU.
- **M2:** the script's own requestAnimationFrame counter keeps running during the idle CPU window. The pacer's 60 Hz polling hides that today. Once ticket C lands, the counter would keep Blink at 60 Hz and inflate idle CPU.
- **M3:** deviceScaleFactor is 1, but the owner's display is Retina, and the app caps dpr at 2. With the emulated fix, moving held 59.7 to 59.9 fps at dpr 2.
- **Small fix (test file only):** call `parkPointer()` before the settle and stillness loop (that loop never touches the mouse) instead of just before the window. Count idle frames from WebGL `clear` calls with no requestAnimationFrame loop of the script's own during the idle CPU window. Optionally add `--dpr`.
