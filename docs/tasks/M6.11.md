So `rebuildProjection` is unchanged (no checkpoints); the checkpoint writes live on the boot path (`rebuildStaleProjections`), which is what the follow-up tests exercise. The boot tests reboot over a seeded, fresh projection, which is why the backfill for fresh projects is needed.

## Red round 2

From roborev panel 6682 on PR #345 (medium at `apps/engine/src/storage/rebuild.ts:98`): a fresh projection with missing checkpoints plus a foreign write lock during boot makes the backfill transaction throw "database is locked", which aborts engine startup for a disposable cache.

Added to `apps/engine/test/timelines/checkpoints-followups.test.ts`, describe "boot backfill is best effort under a busy write lock" (log seeded, projection fresh, `checkpoints` emptied, a second connection holds `BEGIN IMMEDIATE`):
- `rebuildStaleProjections does not throw, keeps the projection, and writes nothing` (connection with a 100 ms busy timeout; must return in under 2 s, not report the project as rebuilt, leave the projection equal and no checkpoint rows).
- `engine boot completes under the lock, and a later seek is right and fills the checkpoints` (`bootInProcess` on the default 5 s timeout must not throw; after the lock is released `stateAtSequence(.., 1250)` equals a full replay and leaves [500, 1000]).

Command: `pnpm exec vitest run --project @taskville/engine apps/engine/test/timelines/checkpoints-followups.test.ts -t "best effort"`

Seen failing (2 failed): both with `expected [Function] to not throw an error but 'Error: database is locked' was thrown`, the right reason. Intended fix: make `backfillCheckpoints` best effort (catch the lock error and skip, as `stateAtSequence`'s upkeep does); a failure in a stale-projection rebuild, which writes the projection itself, is out of scope here. The second test waits the full 5 s default before failing today; after the fix the boot may wait up to that and must then succeed.
