## What it does

`pnpm retro M<n>` reads the milestone through `gh` (`scripts/retro/src/collect.ts`, `execFile`, no shell): milestone, issues, ticket PRs and their commits, CI runs (with earlier attempts of re-runs), board fields from project 2 (GraphQL), and each ticket's `docs/tasks/<KEY>.md` from the default branch. It reduces them to a snapshot with no logins, names, emails, or avatars, redacts the owner login from task-report text, and renders `docs/retros/TEMPLATE.md` to `docs/retros/M<n>.md`. Everything after `collect.ts` is pure and tested.

Options: `--from <snapshot.json>` (offline; renders as of the snapshot's `recordedAt` unless `--now`), `--record <snapshot.json>`, `--out <file>`, `--now <ISO>`. It refuses to write a report whose Mermaid does not validate, and keeps every `*(written)*` section of an earlier report (CommonMark-aware fences, CRLF-safe; a written section the template dropped is appended, never lost).

## Definitions (stated in the report too)

- Ticket: a milestone issue titled `[<KEY>]`; gates, decision tickets, and `Status:` PRs are not tickets.
- Start: earliest author date among the ticket PR's commits (author dates survive rebases; the branch itself is deleted on merge). End: that PR's merge. The merged PR wins over superseded ones.
- Planned: created by the milestone's first ticket commit; added: created after. Split: not measured (GitHub has no record of it).
- Days are UTC. Open tickets are counted at the end of each day; in progress per day is the most tickets worked on at one moment that day (M1 so far: 4, at 01:41 UTC).
- Review outcome, from the task report's `roborev:` field (no GitHub reviews exist): an explicit `**Review outcome:**` field wins; escalation words mean escalated; a round (split at "re-review") with a positive medium-or-higher count and a recorded "fixed" is a fix round; two such rounds are "more than one fix round", listed under the chart; "pass" with nothing fixed is first pass; anything else is not measured and listed.
- CI failures, re-runs, flakes: runs on ticket branches only; a flake is a re-run that succeeded after a failed attempt; cancelled runs are not failures.
- NOT RUN: done tickets whose report lists something NOT RUN; not measured if any done ticket's report does not say. Security findings by severity: not measured (reports do not separate security from bug findings).

## Outside Owns, and why

- `vitest.config.ts` (+1 project) and `tsconfig.json` (+`scripts/*/src`, `scripts/*/test`): without them the tests neither run in `pnpm check` nor typecheck.
- `docs/retros/TEMPLATE.md`: one note line under the Gantt, parallelism, cycle-time, and review charts (`{{timeline_note}}`, `{{parallel_note}}`, `{{cycle_note}}`, `{{review_note}}`), and the parallelism y-axis bound moved to `{{parallel_axis_max}}`. Without the notes, a missing value (for example no merged L tickets) could only be drawn as 0 in a chart, which would read as a measurement; the axis bound must be at least 1 for the chart to be valid when nothing ran.

No new dependency: the Mermaid check is a small validator for the three diagram types the report uses (gantt, xychart-beta, pie), stricter than Mermaid (tasks must sit in a section; values must fit the y-axis). `@mermaid-js/parser` does not cover gantt or xychart, and full `mermaid` needs a DOM.

## Follow-ups for the lead

- M1 ran within one UTC day so far, so the daily burn-down and parallelism charts have a single point; an hourly bucket option would show more for fast milestones (not built: the template and README specify days).
- A `**Review outcome:**` line in `docs/tasks/README.md`'s format would make review outcomes exact instead of parsed; the generator already reads it. M1.10 and M1.11 are "not measured" today because their reports say findings were fixed without severities.
- Re-recording the snapshot needs `biome check --write` on it afterwards (Biome's JSON layout differs from `JSON.stringify`).

## Lessons

- A per-day "in progress" count over-reports parallelism badly when a milestone moves fast: 11 tickets touched the same day, but at most 4 ran at once. Count overlap at an instant, not presence in a bucket.
- Free-text review records are hard to classify honestly: each rule tightening (zero counts, a fix per round, re-review split) came from a reviewer finding a phrasing that broke the previous rule. Prefer a structured field, and keep "not measured" as the default.
- `pnpm -s` is rejected by pnpm 12 (`unexpected argument '-s'`); run scripts without it.
