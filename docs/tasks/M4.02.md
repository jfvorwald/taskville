- **Known limitations:**
  - Decision #271: after fall-through (timeout or no viewer) the request stays open and `answerable: true` in the projection, but the bridge no longer holds it. A terminal No after fall-through is unobservable, so the request waits for a matching PostToolUse or the next engine start. An unheld request is recorded from `taskville:bridge-unheld`, so the reducer never marks it answerable.
  - Identical tool input twice in one prompt stays red until the next engine start (the #116 conservative rule: an ambiguous match closes nothing).
  - A stale identical auto-approved PostToolUse could close a later request as allow (L3).
  - Viewer presence counts CLI-token streams (L2).
  - The bridge remembers the last 1,000 requests (never a still-held one). When a request is forgotten, its session is marked lossy (at most 1,000 such sessions); once a session falls off that set, no PostToolUse closes anything until restart.
  - A request the projection merged into another ("one prompt, one red state") is never resolved by the bridge.
  - M2: a forged bridge request can replace a telemetry card, and its abort resolves the merged record.
  - Caps: at most 64 held responses and 262,144 serialized input characters per held request; larger or later requests are recorded as unheld and answered at once with the empty 2xx. A bridge body over 1 MiB is 413.
  - `observeHook` and the serve composition are not wired yet; M4.04 (#61) does both, with M3 and N6.
- **Lessons:** A pinned route table and a pinned 403-before-401 order are cheap to find and expensive to find late; the red phase should run its security tests against the real middleware order, and wiring should be a line in the red commit's test changes, not an implementer's exception. A bound on remembered state needs a fail-closed rule for what happens when it overflows, decided with the bound.
