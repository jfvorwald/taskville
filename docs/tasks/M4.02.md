- **Known limitations:**
  - After fall-through (timeout or no viewer) the request stays open and `answerable: true` in the projection, but the bridge no longer holds it: `lookup` returns undefined and `decide` returns false (decision #271 defaults). A terminal No after fall-through cannot be seen, so the request waits for a matching PostToolUse or the next engine start. An unheld request (no viewer) is recorded from `taskville:bridge-unheld`, so the reducer never marks it answerable.
  - The bridge remembers the last 1,000 requests to match a PostToolUse. A session that lost one is never attributed a PostToolUse again (the request then expires at the next start), so a forgotten duplicate cannot make an ambiguous match look unique.
  - A request the projection merged into another ("one prompt, one red state") is never resolved by the bridge, because resolving its ID would close the record it merged into.
  - `PermissionBridgeOptions.pipeline` is accepted but unused: `IngestPipeline` refuses the `taskville:` source, so the bridge commits through `commitEngineEvent`.
  - `observeHook` is not called by any route yet; M4.04 calls it from the telemetry route.
- **Lessons:** A pinned route table and a pinned 403-before-401 order are cheap to find and expensive to find late; the red phase should run its security tests against the real middleware order, and wiring should be a line in the red commit's test changes, not an implementer's exception.
