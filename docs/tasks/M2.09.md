## What it does (`apps/engine/src/sources/git/**`)

- **Roots:** every project's roots from the project registry are read each tick, so projects added at runtime are picked up. A root is watched only when it is a repository's top level (`git rev-parse --show-toplevel`, compared after `realpath`). A root that is not a repository is retried after 60 s.
- **Triggers:** a scan runs every 5 s and, with a 250 ms debounce, when files change under `<git common dir>/refs` (recursive `fs.watch`) or `packed-refs`. Scans of one repository never overlap, and a queued scan is shared.
- **Reads, read-only:**
  - `git for-each-ref --count=1000 refs/heads refs/remotes`. Symbolic refs are skipped; tags are not watched.
  - `git log -z --max-count=N --ignore-missing --end-of-options <tips> ^<old tips> --`.
- **Never changes the repository:** no fetch, checkout, or index write.
- **How git is run:**
  - `execFile` with an argument array; 10 s timeout; 16 MiB output cap.
  - `GIT_OPTIONAL_LOCKS=0` and `GIT_TERMINAL_PROMPT=0`.
  - Every inherited `GIT_*` variable is dropped (a stray `GIT_DIR` would redirect every command).
  - `-c core.fsmonitor=false -c log.showSignature=false`, so repository config cannot make git run another program.
  - Ref names never reach the argument list; only validated object names do, after `--end-of-options`. A test asserts the shape of every `git log` argument list.
- **Events, through the ingest pipeline** (validation, masking of subjects and ref names, dedupe, broadcast):
  - `git.commit { repo, sha, parents, subject? }` and, for two or more parents, also `git.merge { repo, sha, parents }`. Dated at the committer date; IDs `commit:<sha>` and `merge:<sha>`.
  - `git.ref_moved { repo, ref, from?, to }`, dated when observed. A first observation has no `from`. ID `ref:<refKey>:<from|none>:<to>:<observed ms>`, where `refKey` is 16 hex characters of SHA-256 of the raw ref name.
  - `sourceId` is `git:<16 hex of SHA-256 of the repository path>`; `repo` is the repository path.
- **Bounds:**
  - A repository with nothing recorded gets its newest **200** commits across all branches.
  - A later scan records at most **1,000** new commits (a larger fetch records its newest 1,000).
  - At most 1,000 branch refs.
- **Restarts:** before a repository's first scan, the last recorded tips are restored from the project's log (from each move's `sourceEventId`, which is stored unmasked), so only changes made while the engine was down are reported, with their `from`. Commit events are idempotent (`commit:<sha>`). A recorded tip whose commit was collected is skipped (`--ignore-missing`).
- **serve:** `taskville serve` starts the watcher after listening and stops it, waiting for scans in progress, before closing the engine. This is a forced extra path in `apps/cli/src/commands/serve.ts`, with a test in `apps/cli/test/integration.test.ts`.

## For the lead

1. **Source ID:** the lead's note suggested an engine-owned `taskville:*` source, but the ingest pipeline's producer policy rejects reserved sources, and engine events written around the pipeline skip masking (L-38). Git subjects and ref names are user text. So events go through the pipeline under `git:<hash>`; events.md already lists `git:<repo>` as an example source ID. Consequence: as before, any producer holding the CLI token can post `git.*` events (they are "Any" sender types in events.md). Nothing answerable or attention-raising depends on them.
2. **Roots inside a larger repository are not watched.** This guards against a home directory under version control being taken for the project, but a project rooted at a monorepo package gets no git events. Allowing it, scoped to the root's path, would be a follow-up or a decision.
3. **Historical merges:** the first scan emits `git.merge` for merges among the newest 200 commits. The M3 merge celebration should compare `occurredAt` with the time it was observed, so an engine start does not celebrate old merges.
4. **Deleted branches** emit nothing: the protocol has no ref-deleted event.
5. **Restore cost:** restoring tips reads the project's whole log once per repository per engine start. That is fine at current sizes; an index by source would make it constant.

## Lessons

- A ref-name injection test with full names (`refs/heads/--output=x`) cannot fail, because a full ref name always starts with `refs/` and is never read as an option. It passed with both defenses removed. The test that bites asserts the shape of every argument list the watcher passes to git.
- Text that ingest may mask is not an identity: restoring branch tips from the stored `payload.ref` broke for a branch whose name looked like a token. The unmasked ID field (`sourceEventId`) carries a key of the raw name instead.
- Dating a first-seen ref at its tip's commit time made restarts deduplicate neatly, but it presented an unobserved move as a recorded fact (roborev high). Restoring state from the log removed the need for that trick.
